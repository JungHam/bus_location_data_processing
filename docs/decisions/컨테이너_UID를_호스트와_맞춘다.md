# 결정 기록 (초안): 컨테이너 UID를 호스트 UID와 맞춘다

> 상태: **확정 (2026-10-21 직접 읽고 확정). Linux에서는 아직 검증 전** · 작성일 2026-10-21
> 번호 미배정. 프로젝트의 ADR 8편(001~008) 번호는 고정이라 이 기록은 번호를 붙이지 않았다. ADR로 승격할지는 W11 "ADR 정리"에서 정한다.
> 검증 범위: macOS(Docker Desktop)에서 작성했다. 아래 Linux 동작은 Docker·Linux 권한 모델에 대한 설명이고 Linux에서 직접 재현해 보지 않았다.

## 맥락
- 로컬 개발은 macOS, 실제 배포는 Linux를 가정한다.
- `docker-compose.yaml`은 프로젝트 루트(`bus_location_data_processing/`)에 있고, `src/`·`data/`·DAG·로그를 컨테이너에 bind mount 한다.
- Airflow 컨테이너는 `user: "${AIRFLOW_UID:-50000}:0"`으로 root가 아닌 UID로 돈다. `airflow-init`은 root(0:0)로 돌며 `chown -R ${AIRFLOW_UID:-50000}:0 /opt/airflow/`를 실행한다.

## 문제
Linux는 파일 권한을 사용자 이름이 아니라 숫자 UID로 비교하고, bind mount는 UID를 변환하지 않는다. 그래서 기본값(50000)으로 두면 다음이 생긴다.
1. 호스트에 없는 폴더를 마운트하면 Docker가 root 소유로 만든다. 컨테이너(50000)가 거기에 쓰지 못할 수 있다.
2. 컨테이너가 만든 파일은 호스트에서 50000 소유로 보여, 내 계정(예: 1000)이 수정하거나 지우지 못한다.
3. init의 `chown -R`이 마운트한 `src/`·`data/`까지 따라 들어가 호스트 코드의 소유자를 50000으로 바꾼다.
macOS의 Docker Desktop은 소유자를 호스트 사용자로 맞춰 보여 주므로 위 문제를 개발 중에는 겪지 못한다.

## 결정
- `.env`에 `AIRFLOW_UID=$(id -u)`로 호스트 사용자의 UID를 넣는다. 컨테이너가 내 UID로 돌아 생성 파일도 내 소유가 되고, init의 `chown`은 소유자를 바꾸지 않는 동작이 된다.
- `dags/`, Airflow 로그용 폴더, `config/`, `plugins/`는 `docker compose up` 전에 내 계정으로 `mkdir` 한다.
- Airflow 로그는 기존 수집기 로그(`logs/`)와 섞이지 않도록 별도 폴더로 분리한다.

## 검토한 대안
| 대안 | 기각 이유 |
|---|---|
| 기본값 50000 유지 | 위 문제 1~3이 Linux에서 생긴다. 특히 3은 호스트 코드의 소유권이 바뀐다. |
| 호스트 폴더를 `chmod 777` | 권한 문제는 가려지지만 무엇이든 쓰기 가능한 상태가 된다. 배포 환경에 쓸 수 없다. |
| 코드를 bind mount 하지 않고 이미지에 포함 | UID 문제는 사라지지만 코드를 고칠 때마다 재빌드해야 한다. 개발 단계에는 과하고, 배포 단계 구성으로는 적합하다. |

## 결과 (예상)
- 장점: 호스트에서 코드를 고치는 데 권한 문제가 없고, 호스트 파일 소유권이 바뀌지 않는다.
- 단점: UID를 `.env`에서 맞추는 것을 잊으면 문제가 되살아난다. 서버마다 UID가 다를 수 있어 서버 설정 절차에 이 한 줄을 넣어야 한다.
- 확인 방법: Linux에서 `up` 후 `ls -ln dags <airflow 로그 폴더> src data`로 소유자 UID가 내 UID와 같은지 본다.

## 열린 질문
- 배포 환경(W10 EC2)에서 Airflow를 어떤 사용자로 돌릴지, 코드를 마운트할지 이미지에 넣을지는 아직 정하지 않았다. (ADR-008 범위)
